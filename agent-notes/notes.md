# Notes

## Decision: links are parsed out of Markdown, not stored separately

The first version of notes stored links in a `note_link` table
(`from_note_id`, `to_note_id`) and the API/editor took a `:links` array of note
ids. The user asked for links to be parsed out of the note content instead:
a note is Markdown and writes `[[Another note's title]]` to point at it.

The implementation now:

- parses `[[Title]]` references out of every note's content when a note is
  loaded (`clai.daemon.postgres.notes/link-titles`), and
- resolves those titles against the stored titles to produce both `:links`
  and `:backlinks`.

Nothing about a link is persisted. `schema/schema.sql` no longer defines
`note_link` and drops it (`DROP TABLE IF EXISTS note_link`) so an existing dev
database does not keep a stale, unused table. `note` is the only note table.

Why derive rather than materialize:

- A link always matches the text. There is no window where content and
  `note_link` disagree, no transaction to write links in, and no failure mode
  where a link points at a deleted note.
- A reference to a note that does not exist yet is harmless: it resolves as
  soon as the target is written, without having to re-save every note that
  mentions it. A materialized table would show no backlinks for
  forward-declared links.
- The code is much smaller: no `NoteRef` schema, no `replace-links!`, no link
  SQL, no delete cascades.

The cost is that `load-note` scans `id, title, content` for every note and
resolves links in Clojure. That is fine for a personal knowledge base and keeps
one source of truth for the syntax. If it ever gets slow, the cheap next step
is a materialized cache maintained on write, but it should keep the content as
the source of truth.

`load-note`, `create-note`, and `update-note` all use the same resolution
(`note-detail`), and `list-notes`/`search-notes` stay link-free so list and
search responses remain one query each.

## Titles are unique

A title is the addressing key, so two notes with the same title would make
`[[Title]]` ambiguous. `schema/schema.sql` creates
`note_title_unique_idx ON note (lower(trim(title)))`, and `create-note` /
`update-note` also check first (`ensure-title-free!`) so the API and tools get
a readable `ex-info` ("A note titled ... already exists", HTTP 400) instead of a
raw unique-violation. Resolution lower-cases and trims titles, so `[[bm25]]`
finds "BM25" and the unique index matches the same rule.

A note's reference to its own title is dropped from its `:links` (and produces
no self-backlink), since a self-link has no meaning in the UI.

## Syntax

`#"\[\[([^\[\]\r\n]+)\]\]"` — title characters stop at brackets and newlines,
so a stray `[[` or a multi-line paragraph cannot swallow the rest of a note.
Blank titles are ignored. Duplicate references are collapsed in
first-appearance order. Code spans/fences are *not* special-cased in storage
(Clojure parsing Markdown is not worth it); the web renderer's remark plugin
does skip code nodes, so a screenshot of the syntax renders as code.

## Search and the BM25 index

`schema/schema.sql` creates `note_content_bm25_idx`
(`USING bm25(content) WITH (text_config = 'english')`) inside a `DO` block that
first checks `pg_extension` for `pg_textsearch`. `ensure-schema!` applies the
DDL on every process start, and the file deliberately stays applicable to a
server without the extension (see `agent-wiki/database.md`), so the index has
to be conditional.

Search has to match that:

- With the extension, `search-notes` runs
  `content <@> to_bm25query(?, 'note_content_bm25_idx') < 0`, ordered by the
  same expression. The index is named explicitly because `content <@> ?` with a
  bound parameter fails ("no BM25 index found for text <@> text expression") —
  only a literal or a `bm25query` value resolves the operator. Scores are
  negative, and `0` means "no match", hence the `< 0` filter.
- Without the extension, it falls back to
  `position(lower(?) in lower(content)) > 0` ordered by `updated_at`. No
  ranking, but no error either. Chosen over `ILIKE '%' || ? || '%'` so user
  input cannot inject `%`/`_` wildcards.

Which mode a datasource uses is remembered in the private `bm25-datasources`
atom (positive answers only, so installing the extension later is picked up).

## HTTP surface

Six routes in `clai.daemon/http.clj`, following the git-repo pattern
(route -> `clai.agent.core` wrapper -> storage namespace). Five of them are
generated by `crud-routes` from `note-spec`, `search` is a row of its own in
`special-routes` -- see `http-routing.md`:

    GET    /api/notes
    POST   /api/notes
    GET    /api/notes/search?q=&limit=
    GET    /api/notes/<id>
    PUT    /api/notes/<id>
    DELETE /api/notes/<id>

`/api/notes/search` is listed before the `/api/notes/:noteId` template, which
would otherwise read `search` as an id. A blank or missing `q` is a 400 with "A
search query is required" rather than a storage validation error.

`POST` and `PUT` bodies are `{title, content}` only. Links come from the
content, so there is no links field in the API (a leftover one is ignored by
`prepare-note`, since it selects only the note's own fields before validating).

The agent wrapper exists for consistency with git repos/agent configs (and
gives the routes something tests can `with-redefs`). The chat loop does not
use the wrappers: its tools call `clai.daemon.postgres.notes` directly (see
below).

## Agent tools

`src/clai/agent/tools/builtin/notes.clj` adds five built-in tools --
`notes_list`, `notes_search`, `notes_read`, `notes_update`, and
`notes_delete` -- which `clai.agent.tools.builtin/built-in-tools` appends to
the default set. A session's `:tools` selection can still drop them like any
other built-in.

The handlers call `clai.daemon.postgres.notes` directly with `(:postgres ctx)`.
Going through `clai.agent.core` would be a circular require (`agent.core`
already requires the built-in tools), and going through `/api/notes` would
need the daemon running for a CLI session. A context without a client throws
an `ex-info`, which `clai.agent.tools.invoke` turns into `Error: ...` for the
model.

`notes_update` is a partial update: storage replaces the whole note, so the
tool reads the stored note and merges the given fields over it. It takes only
`title` and/or `content`; links are not an argument because they are whatever
the saved content references. The tool description tells the model to write
`[[Note title]]` in the content.

`notes_read` renders timestamps, links, backlinks, and the content, cutting
content past 20,000 characters (there is no paging argument). List and search
results render a 200-character one-line preview per note instead of the
content. `common/format-timestamp` and `common/truncate` were moved out of
`openproject.clj` so the two tool namespaces share them.

Tests in `test/clai/agent/tools/builtin/notes_test.clj` `with-redefs` the
storage functions, so they need no database; the storage integration round
trip stays in `notes_test.clj` under `CLAI_TEST_POSTGRES_URL`.

## Web UI

The Notes page (`web/src/components/NotesPage.jsx`, reachable from the topbar)
is a two-column page in the git-repo page's shape: the searchable list on the
left, the open note -- or its editor -- on the right.

- `web/src/useNotes.js` owns the data. It keeps the full list (`stored`), the
  search results (`results`, null when no query is active), and the selected
  note's detail. `notes` is `results ?? sortNotes(stored)`, which is what the
  list renders.
- Search is debounced 250ms in a `useEffect` keyed on the query, with an
  `AbortController` per query so a slow response cannot overwrite newer
  results. It asks for `limit=50` rather than the endpoint's default 20.
- `select` guards against out-of-order detail responses with a sequence ref.
  `saveNote` replaces the row in both lists and selects the saved detail;
  `deleteNote` removes the row from both and clears the detail when it was the
  open one.
- `web/src/notes.js` holds the pure note-shape helpers: `formToNoteInput`
  mirrors `prepare-note` (trim, reject blanks), `noteToForm` round-trips a
  detail (title and content only), `sortNotes` re-sorts after a write,
  `titleLookup` maps ids to titles for the link chips, and `titleIds` /
  `resolveTitle` map a `[[Title]]` reference back to a note id the way storage
  resolves it (lower-cased, trimmed). `web/src/notes.test.js` covers them.
- `web/src/noteLinks.js` (`noteLinks.test.js`) is the wiki-link syntax: it
  parses `[[Title]]` titles, splits text into plain/link pieces, and exports
  `remarkNoteLinks`, the remark plugin that turns resolved references into
  `note:<id>` links in rendered Markdown. It skips code nodes so code samples
  stay literal.
- `web/src/components/Markdown.jsx` takes optional `resolveNote` and
  `onOpenNote` props. The notes page passes them, so a rendered reference opens
  the note in the page; chat/update views pass neither, so their Markdown is
  unchanged.
- The editor has no link picker. It parses the content as you type and shows
  the references it finds, with a dashed chip for a title that has no note yet.
  It always sends `title` and `content` (there is nothing else to send).
- Form CSS reuses the `.config-form` classes the git page already reuses; the
  page shell uses `.list-page` / `.list-panel`, renamed from `git-page` /
  `git-panel` when the notes page started sharing them. The old link-picker CSS
  (`.notes-editor__add-link`, `.note-link-chip__remove`) was removed with it.

  resolution, search.
