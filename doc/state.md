# Session storage format

This document describes the on-disk format used by `clai.state`
(`src/clai/state.clj`) to persist ACP sessions: where the files live, what
they contain, how they are read and written, and what guarantees (and
non-guarantees) the implementation provides.

## Overview

`clai` is stateless between prompts except for one thing: *sessions*. Every
ACP session gets a single EDN file holding the session parameters and the
full message history, so a client can disconnect, restart the agent, and
later `session/load` the session back into place.

There is exactly one file per session, and the file *is* the session: there
is no index, no database, and no in-memory registry. Every read is a file
read; every mutation is a read-modify-write of the whole file.

## Location and naming

```
~/.local/clai/sessions/
  <sessionId>.edn
```

* The directory is `~/.local/clai/sessions`, resolved by
  `clai.state/sessions-dir` as `$HOME/.local/clai/sessions` (falling back to
  the `user.home` system property when `$HOME` is unset). `XDG_DATA_HOME` is
  *not* honored, unlike the config loader in `clai.config`.
* The file name is the session id plus `.edn`. Session ids are random UUID
  strings generated by `clai.state/new-session-id`, but any non-empty string
  works — `register-session` persists a session under an id chosen by the
  client, and ids that are not UUIDs simply produce differently named files.
* The directory is created lazily (and recursively) on the first write. A
  missing directory is not an error for reads; it just means "no sessions".
* `list-sessions` walks the directory with `file-seq` and keeps every regular
  file whose name ends in `.edn`, so it also picks up files in
  subdirectories and any stray `.edn` file dropped in there.

## File contents

Each file is a single EDN map. A representative file:

```clojure
{:sessionId "3f2b1c8e-1a2b-4c3d-9e4f-5a6b7c8d9e0f",
 :cwd "/home/me/project",
 :model "gemma3",
 :params {:temperature 0.7},
 :createdAt "2025-01-02T03:04:05.678901Z",
 :updatedAt "2025-01-02T03:05:06.789012Z",
 :history
 [{:role "system", :content "You are clai."}
  {:role "user", :content "read foo.txt"}
  {:role "assistant",
   :content "",
   :tool_calls
   [{:id "call_1",
     :function {:name "read_file", :arguments {:path "foo.txt"}}}]}
  {:role "tool",
   :content "hello",
   :name "read_file",
   :tool_call_id "call_1"}
  {:role "assistant", :content "It says hello."}]}
```

(The pretty-printer separates some map entries with commas. Commas are
whitespace in EDN, so the file is ordinary EDN either way.)

### Top-level keys

| Key         | Type                       | Presence | Meaning |
|-------------|----------------------------|----------|---------|
| `:sessionId`| non-empty string           | required | The session id; must match the file name for `load-session` to find it. |
| `:cwd`      | string                     | required | Absolute working directory for tool execution (`clai.agent.loop` hands this to tools as their `:cwd`). |
| `:model`    | string or `nil`            | optional | Model the session chats with. Written by `create-session` / `set-model`; `register-session` omits it entirely. |
| `:params`   | map                        | optional | Arbitrary extra session parameters. Reserved as an extension point: nothing in the agent writes it today, only `set-param` / `set-params`. |
| `:createdAt`| ISO-8601 string            | required | Creation time, UTC (`java.time.Instant` rendered with `str`). |
| `:updatedAt`| ISO-8601 string or `nil`   | optional | Refreshed by every `save-session`, i.e. on every mutation. |
| `:history`  | vector of message maps     | optional | The conversation, oldest first. Absent is treated as empty. |

Unknown top-level keys are permitted and are preserved: `load-session` returns
the map as read, and `save-session` writes back whatever map it is given.

The authoritative description of this shape is the Malli schema
`clai.state/session`; `clai.state/session-summary` is the same map minus
`:history`. These schemas are enforced at runtime by Malli instrumentation
(see `clai.instrument`), so a hand-edited file with missing or mis-typed keys
fails `load-session` rather than being returned as-is.

### Message maps (`:history` entries)

History entries are Ollama chat messages, defined by the schema
`clai.state/message`:

| Key           | Type                          | Presence | Meaning |
|---------------|-------------------------------|----------|---------|
| `:role`       | non-empty string              | required | `"system"`, `"user"`, `"assistant"`, or `"tool"`. |
| `:content`    | string or sequential of maps  | optional | Message text. Strings are what the agent writes; the looser type exists because the history is also accepted straight from clients. |
| `:thinking`   | string or `nil`               | optional | Chain-of-thought returned by a thinking model. Persisted on the final assistant message so `session/load` can replay it as an `agent_thought_chunk`; also part of Ollama's chat-message format. |
| `:images`     | sequential of strings         | optional | Base64 images (Ollama convention). Not written by the agent today. |
| `:tool_calls` | sequential of maps            | optional | Tool calls requested by an `assistant` message, in Ollama's `{:id ... :function {:name ... :arguments {...}}}` shape. |
| `:name`       | string                        | optional | Tool name, on `"tool"` messages written by the agent loop. |
| `:tool_call_id` | string                      | optional | Id of the tool call a `"tool"` message answers; only added when the originating call carried an `:id`. |

The format is intentionally the *provider* format rather than a private one:
`clai.agent.loop` passes `:history` verbatim as the `:messages` field of an
Ollama `/api/chat` request. Anything in the vector must therefore stay
acceptable to the Ollama chat API, and conversely no extra bookkeeping that
the model must not see should be added here (that is what `:params` is for).

What the agent actually writes, in order:

1. `{:role "system" :content <system-prompt>}` — only at session creation,
   and only when the config has a `:system-prompt` or the session's `cwd`
   contains an `AGENTS.md` (whose contents are appended to the configured
   system prompt, or used as the system prompt when none is configured).
2. `{:role "user" :content "..."}` — one per incoming ACP prompt, after ACP
   content blocks are flattened to text by `clai.providers.ollama.acp`.
3. `{:role "assistant" :content "" :tool_calls [...]}` — the model's own tool
   request, stored verbatim so the next round can see it.
4. `{:role "tool" :content "<result>" :name "read_file" :tool_call_id "..."}`
   — one per executed tool call.
5. `{:role "assistant" :content "<final reply>"}` — once the model stops
   calling tools. When the model returned reasoning, the message also carries
   `:thinking "<chain of thought>"`.

## Serialization details

* **Writer**: `clojure.pprint/pprint` with `*print-namespace-maps*` false and
  unlimited `*print-length*` / `*print-level*`, so output is human-readable
  and never elided.
* **Reader**: `clojure.edn/read` with `{:eof nil}`. This is `clojure.edn`, not
  `read-string`, so the file cannot evaluate code and no custom data readers
  are installed (only the built-in `#inst` / `#uuid` readers exist). Only the
  *first* form in the file is read; trailing forms are ignored.
* **Timestamps** are strings, not `#inst` literals: `Instant/now` rendered
  with `str`, e.g. `"2025-01-02T03:04:05.678901Z"`. Because they are
  fixed-format UTC ISO-8601, lexicographic order equals chronological order,
  which is why `list-sessions` can sort by the raw `:createdAt` string.
* **Empty or missing files** read as `nil`, which `load-session` returns
  directly, and `list-sessions` skips.
* **Unreadable files** (malformed EDN, I/O error) are logged
  (`::session-read-failed`) and re-thrown. A single corrupt file therefore
  breaks `load-session` for that id *and* `list-sessions` /
  `list-session-summaries` for everyone, since listing reads every file.
* **No format version field.** There is no `:schemaVersion` or equivalent;
  the shape is expected to change additively (new optional keys), and readers
  should tolerate absent optional keys.

## Writing and durability

* `write-edn-file` writes directly to the target path with `io/writer`, i.e.
  it truncates the existing file and prints into it. There is **no
  temp-file-and-rename**, no `fsync`, and no backup. A crash (or two
  concurrent writers) can therefore leave a truncated or interleaved file.
* Writes are whole-file: a mutation loads the map, changes it in memory, and
  re-prints everything. Large histories mean proportionally more work per
  appended message (an O(n) rewrite of the session file per append).

## Concurrency

Mutation helpers (`append-history`, `set-param`, `set-params`, `set-model`,
`clear-history`) wrap their read-modify-write in `clojure.core/locking` keyed
on the session id, so updates from a single caller sharing one id value are
serialized rather than lost.

Two caveats worth knowing:

* The monitor is the `String` object passed in. Two equal-but-distinct
  `String` instances (e.g. one built by `str`, one from JSON parsing) are
  different monitors, so the lock only serializes callers that share the same
  string instance (or an interned one). It is not a cross-thread guarantee
  based on value equality.
* `locking` is in-process only. Two `clai` processes pointed at the same
  `$HOME` can write the same session file concurrently and last writer wins
  (possibly with a corrupt result). Nothing takes a file lock.

## API surface

All functions live in `clai.state`.

### Lifecycle

| Function | Persists | Returns |
|----------|----------|---------|
| `create-session` `[{:cwd :model :params}]` | New file with `:sessionId`, `:cwd`, `:model`, `:params`, `:createdAt`, `:updatedAt`, `:history []` | The state map |
| `register-session` `[id cwd history]` | New file under a caller-chosen id; `:cwd` defaults to `"."`, `:params {}`, `:createdAt`/`:updatedAt` = now, `:model` absent | The saved state map |
| `load-session` `[id]` / `lookup-session` `[id]` | — | State map, or `nil` if no file |
| `save-session` `[state]` | Whole map at `<:sessionId>.edn`, refreshing `:updatedAt` | The saved state map |
| `delete-session` `[id]` | Removes the file | `true` if a file was removed, else `false` |
| `session-exists?` `[id]` | — | Boolean |

### Reading

| Function | Returns |
|----------|---------|
| `list-sessions` | Vector of full state maps, sorted by `:createdAt` ascending |
| `list-session-summaries` | Same, with `:history` dissoc'd (for session pickers / ACP `session/list`) |
| `session-history` | `:history` vector, or `[]` if the session is unknown |

### Mutation

All of these return the updated full state map, or `nil` (plus a
`::unknown-session` warning log) if the session is not on disk:

| Function | Effect |
|----------|--------|
| `append-history` `[id msg]` | `conj` one message onto `:history`; returns the *message*, or `nil` if unknown |
| `clear-history` `[id]` | Sets `:history` to `[]` |
| `set-param` `[id k v]` | `assoc-in` one entry in `:params` |
| `set-params` `[id m]` | Merges `m` into `:params` |
| `set-model` `[id model]` | Replaces `:model` |

Note the asymmetry: an unknown session is a *silent* no-op for
`append-history` (it warns and returns `nil`), while `load-session` /
`session-history` simply report emptiness. Callers are expected to
`create-session` (or `register-session`) first.

## Relationship to the ACP session lifecycle

`clai.agent` maps protocol calls onto this format:

| ACP call | Storage effect |
|----------|----------------|
| `session/new` | `create-session` with the client's `cwd` and the configured model; appends a system message combining the configured system prompt with the `cwd`'s `AGENTS.md` (when either exists) |
| `session/prompt` | Refuses unknown sessions; otherwise appends the user message(s), then each assistant/tool message the loop produces |
| `session/load` | `load-session`, persists a changed `cwd` if the client supplies one, then replays `:history` to the client as `session/update` chunks (`user` → `user_message_chunk`, `assistant`/`agent` → `agent_message_chunk`, preceded by `agent_thought_chunk` when the message has `:thinking`; `system` and `tool` messages are internal and not replayed) |
| `session/list` | `list-session-summaries`, optionally filtered by exact `:cwd` match |
| `session/resume` | `load-session`, or `register-session` under the requested id when unknown, so resume degrades to "new" instead of erroring |
| `session/delete` | `delete-session` |
| `session/close` | Nothing — history is deliberately kept so the client can load the session again |

## Working with the files by hand

* Inspect a session from a REPL or `clojure -M -e`:

  ```clojure
  (require '[clojure.edn :as edn] '[clojure.java.io :as io])
  (with-open [r (java.io.PushbackReader. (io/reader (io/file (System/getenv "HOME")
                                                             ".local/clai/sessions/<id>.edn")))]
    (:history (edn/read {:eof nil} r)))
  ```

* Grep for a session by its working directory or model:
  `grep -l ':cwd "/path/to/project"' ~/.local/clai/sessions/*.edn`.
* Deleting a file forgets the session (the agent's `session/delete` is just
  `rm`); closing a session does not.
* Hand-editing is only safe while the agent is not mutating that session —
  each mutation rewrites the whole file from the last-read contents, so an
  edit made between a read and a write is lost. Shrinking `:history` by hand
  is a supported way to trim context: the next prompt simply sends the
  smaller history to the model.
* Truncating `:history` to `[]` is equivalent to `clear-history`; removing
  the system message is equivalent to running without a system prompt for
  that session.
